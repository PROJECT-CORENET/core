# CORE — Rust-ядро и нода

Архитектура — [`../АРХИТЕКТУРА.md`](../АРХИТЕКТУРА.md), прогресс — [`../ПРОГРЕСС.md`](../ПРОГРЕСС.md).

Нода CORE — это сервер-ретранслятор децентрализованной сети. Она:

- хранит **зашифрованные** сообщения до доставки (очереди и журналы чатов) — содержимого не видит;
- держит статусы «в сети» (зашифрованные, без истории);
- знакомится с другими нодами, обменивается с ними подписанными описаниями и статистикой (gossip) —
  из этого строится карта сети в приложении.

Любой может поднять ноду; чем больше нод у разных хостеров и в разных странах — тем устойчивее сеть.

## Состав репозитория

| Crate | Что делает |
|---|---|
| `crates/core-proto` | Кадры 16 KiB, сообщения протокола (protobuf через prost-derive) |
| `crates/core-crypto` | Ed25519, X25519, SHA-256 — обёртки над RustCrypto/dalek |
| `crates/core-net` | Noise_NK поверх TCP, адрес `core://…`, клиент (запрос/ответ + события) |
| `crates/core-directory` | Каталог нод: подписанные дескрипторы и статистика, проверка снимков, связи |
| `crates/node` | Нода: mailbox, presence, соседи и gossip, SQLite, TTL |
| `tools/core-cli` | CLI для проверки нод: `ping`, `demo`, `net` |

## Быстрый старт локально

Нужен Rust (stable, 1.80+).

```sh
cargo run -p core-node -- --data-dir ./node-data --listen 127.0.0.1:7443 run
```

В выводе будет адрес ноды:

```
node_id: 6add6d95…
address: core://99739a0f…d271@127.0.0.1:7443
```

В другом терминале:

```sh
cargo run -p core-cli -- ping core://<ключ>@127.0.0.1:7443   # задержка
cargo run -p core-cli -- demo core://<ключ>@127.0.0.1:7443   # очередь + журнал
cargo run -p core-cli -- net  core://<ключ>@127.0.0.1:7443   # сеть глазами ноды
```

## Развёртывание на сервере (Docker)

### Требования

- Linux-сервер с публичным IP (подойдёт VPS за 3–5 $/мес: 1 vCPU, 512 МБ RAM, 10 ГБ диска).
- Docker 24+ с плагином `docker compose`.
- Открытый входящий **TCP-порт** (по умолчанию `7443`).

### Шаги

```sh
# 1. Код
git clone <репозиторий> core && cd core/CORE

# 2. Настройки
cp .env.example .env
nano .env
```

В `.env` обязательно укажите **публичный адрес** — по нему к ноде будут подключаться клиенты и другие ноды:

```sh
CORE_PUBLIC_HOST=203.0.113.10:7443      # IP или домен сервера + порт
CORE_NAME=Amsterdam-1                   # имя на карте сети (необязательно)
CORE_REGION=NL                          # код страны на карте (необязательно)
CORE_BOOTSTRAP=core://…@…:7443          # другие ноды — см. следующий раздел
```

```sh
# 3. Открыть порт (пример для ufw)
sudo ufw allow 7443/tcp

# 4. Запуск (первый раз образ собирается ~2–5 минут)
docker compose up -d

# 5. Адрес вашей ноды — его вы даёте клиентам и владельцам других нод
docker compose exec node core-node info
```

```
node_id: 3f1c…
address: core://a8b2…91fe@203.0.113.10:7443
```

```sh
# 6. Проверка
docker compose ps                     # STATUS должен стать (healthy)
docker compose logs -f node           # логи, см. раздел «Логи»
```

Вместо локальной сборки можно взять готовый образ из GitHub Container Registry — в `.env`:
`CORE_IMAGE=ghcr.io/<owner>/core-node:latest`, затем `docker compose pull && docker compose up -d`.

## Подключение к другим нодам

### Адрес ноды

Каждая нода имеет адрес вида

```
core://<x25519-ключ ноды, 64 hex>@<host>:<port>
```

Ключ в адресе — то, что защищает от подмены: подключение к ноде с другим ключом не пройдёт
(Noise-рукопожатие провалится), даже если злоумышленник перехватит IP. Поэтому адреса передают
целиком, а не просто `host:port`.

Узнать адрес ноды: `core-node info` (или `docker compose exec node core-node info`).

### Bootstrap

Чтобы нода вошла в сеть, ей нужно знать **хотя бы одну** другую ноду — это bootstrap:

```sh
# .env (Docker)
CORE_BOOTSTRAP=core://aaaa…@198.51.100.7:7443,core://bbbb…@node.example.org:7443
```

```sh
# или флагом
core-node run --bootstrap core://aaaa…@198.51.100.7:7443,core://bbbb…@node.example.org:7443
```

```toml
# или в node.toml
bootstrap = ["core://aaaa…@198.51.100.7:7443", "core://bbbb…@node.example.org:7443"]
```

Несколько адресов через запятую — если одна bootstrap-нода недоступна, сработает другая.

### Что происходит дальше

1. Нода подключается к bootstrap-нодам и **представляется**: присылает свой подписанный дескриптор
   (ключи, адреса, имя, регион) и доказывает владение ключом в этом соединении.
2. Ноды обмениваются всем, что знают о сети (**gossip**): дескрипторы и статистика других нод
   расходятся по сети за несколько секунд. Каждая запись подписана своей нодой — подделать её нельзя.
3. Узнав о новых нодах, нода **сама подключается** к ним, пока не наберёт `max_peers / 2` исходящих
   соединений (по умолчанию 4). Входящих может быть до `max_peers × 2`.
4. Статистика (соседи, число клиентов, нагрузка) публикуется раз в `gossip_interval_secs`
   и сразу при изменении соседей.
5. Неудачные подключения повторяются с растущей паузой (2 с → 4 с → … → 10 мин).

Достаточно одной bootstrap-ноды — остальную сеть нода найдёт сама. Связь двусторонняя:
не нужно прописывать вашу ноду у соседей.

### Несколько адресов у одной ноды

Если к ноде из разных мест подключаются по разным адресам (публичный IP для клиентов, внутренний
адрес в docker-сети/VPN для соседей), перечислите их все:

```sh
CORE_PUBLIC_HOST=203.0.113.10:7443                     # первый адрес — для клиентов
CORE_EXTRA_ADDRESSES=10.0.0.5:7443,node-a.internal:7443 # дополнительные
```

Все адреса попадают в дескриптор; соседи пробуют их по порядку.

### Как убедиться, что нода в сети

```sh
core-cli net core://<ключ вашей ноды>@203.0.113.10:7443
```

```
🗺️  сеть глазами 9d823a17 (3 записей, подписи верны у 3)
  🟢 ▲ 48f3b044 Charlie  FI  клиентов≈0    нагрузка=0/10 аптайм=4с  …
  🟢 ▲ 6d29a29e Alpha    NL  клиентов≈0    нагрузка=0/10 аптайм=12с …
  🟢 ▲ 9d823a17 Bravo    DE  клиентов≈0    нагрузка=0/10 аптайм=4с  … ← эта нода
🔗 связи (подтверждены обеими сторонами): 3
```

В логах ноды: `🔗 peer connected (outbound) node=…` и `📡 gossip tick: peers=N known_nodes=M`.

## Своя сеть из нескольких серверов

Пример: три сервера A, B, C.

```sh
# Сервер A — первая нода, bootstrap пустой
CORE_PUBLIC_HOST=203.0.113.10:7443
CORE_NAME=A
docker compose up -d
docker compose exec node core-node info      # → core://AAAA…@203.0.113.10:7443

# Сервер B — знает A
CORE_PUBLIC_HOST=198.51.100.7:7443
CORE_BOOTSTRAP=core://AAAA…@203.0.113.10:7443

# Сервер C — достаточно знать A (или B): о второй ноде узнает через gossip
CORE_PUBLIC_HOST=192.0.2.44:7443
CORE_BOOTSTRAP=core://AAAA…@203.0.113.10:7443
```

Через несколько секунд все три ноды соединены друг с другом. Рекомендация: указывайте 2–3 bootstrap-ноды
у разных хостеров — тогда падение одной не мешает новым нодам войти в сеть.

### Автоматически: GitHub Actions (`deploy.yml`)

Боевая сеть разворачивается workflow [`.github/workflows/deploy.yml`](.github/workflows/deploy.yml)
на своих серверах через self-hosted раннеры:

| Нода | Раннер (метка) | Адрес | Регион |
| ---- | -------------- | ----- | ------ |
| N1 (главный) | `proxy` | 188.225.72.79:7445 | RU |
| N2 | `nl` | 141.98.235.172:7445 | NL |
| N3 | `vn` | 213.171.4.253:7445 | RU |
| I1 | `imirjar` | 91.215.121.220:7445 | RU |

- Запуск: сам после успешного `node` на `main` (образ этого коммита `sha-xxxxxxx` из GHCR) или вручную —
  Actions → **deploy** → Run workflow (тег образа: `latest`, `sha-…`, версия).
- Шаги: `identity` — на каждом сервере получить адрес ноды (ключи создаются один раз в томе `core-node-data`
  и дальше не меняются) → `run` — перезапустить контейнер `core-node` с bootstrap из адресов всех остальных
  нод и дождаться `healthy` → `verify` — с N1 пропинговать каждую ноду по публичному адресу.
- Итог в Summary запуска: таблица нод и готовый `nodes.json` для `PROJECT-CORENET/nodes` (он же — артефакт `nodes-json`).

Что нужно на каждом сервере: зарегистрированный раннер с нужной меткой, Docker, пользователь раннера в группе
`docker`, открытый TCP-порт 7445. Добавить ноду — строка в списке `nodes` в начале `deploy.yml`.
Ключ ноды — в томе `core-node-data`: удалите том, и у ноды будет новый адрес (обновите `nodes.json`).

## Локальная тестовая сеть (testnet)

Три связанные ноды на одной машине:

```sh
docker compose --profile testnet up -d
```

| Нода | Имя | Адрес для клиентов на хосте |
|---|---|---|
| testnet-1 | Alpha (NL) | `core://eaf9b12457fda0aade8aa28641f3117a20d3238b5dc0687cb0f7fc58ea251b61@127.0.0.1:17441` |
| testnet-2 | Bravo (DE) | `core://710910b6e3dc90c3200e0a71372b738ae83e57499e27596830f5cf70a4eaf706@127.0.0.1:17442` |
| testnet-3 | Charlie (FI) | `core://83d76b80be64a0953a941f23e9471879e608b2f81640b5c7478fe5d669127c3a@127.0.0.1:17443` |

Адреса постоянные: ключи testnet-нод выводятся из публичных зёрен (`CORE_IDENTITY_SEED`) —
**никогда не используйте это в настоящей сети**: кто знает зерно, тот владеет нодой.

Charlie знает только Bravo — проверьте, что он сам нашёл Alpha:

```sh
cargo run -p core-cli -- net core://83d76b80be64a0953a941f23e9471879e608b2f81640b5c7478fe5d669127c3a@127.0.0.1:17443
```

Остановить: `docker compose --profile testnet down` (добавьте `-v`, чтобы стереть данные).

## Без Docker: systemd

```sh
cargo build --release -p core-node
sudo install -m 755 target/release/core-node /usr/local/bin/
sudo useradd --system --home /var/lib/core-node --create-home core
```

`/etc/systemd/system/core-node.service`:

```ini
[Unit]
Description=CORE network node
After=network-online.target
Wants=network-online.target

[Service]
User=core
Environment=CORE_DATA_DIR=/var/lib/core-node
Environment=CORE_PUBLIC_HOST=203.0.113.10:7443
Environment=CORE_BOOTSTRAP=core://AAAA…@198.51.100.7:7443
Environment=RUST_LOG=info
ExecStart=/usr/local/bin/core-node run
Restart=always
RestartSec=3
LimitNOFILE=65536
NoNewPrivileges=true
ProtectSystem=strict
ReadWritePaths=/var/lib/core-node

[Install]
WantedBy=multi-user.target
```

```sh
sudo systemctl daemon-reload && sudo systemctl enable --now core-node
journalctl -u core-node -f
```

## Конфигурация — все параметры

Порядок приоритета: **флаг командной строки → переменная окружения → `node.toml` → значение по умолчанию**.
`node.toml` создаётся в каталоге данных при первом запуске.

| `node.toml` | Переменная / флаг | По умолчанию | Описание |
|---|---|---|---|
| — | `CORE_DATA_DIR` / `--data-dir` | `./node-data` (в Docker `/data`) | Каталог: ключи, конфиг, база |
| `listen` | `CORE_LISTEN` / `--listen` | `0.0.0.0:7443` | На каком адресе слушать |
| `public_host` | `CORE_PUBLIC_HOST` / `--public-host` | — | Публичный `host:port` (первый адрес ноды) |
| `extra_addresses` | `CORE_EXTRA_ADDRESSES` / `--extra-addresses` | `[]` | Дополнительные адреса, через запятую |
| `name` | `CORE_NAME` / `--name` | `""` | Имя на карте сети (до 64 байт) |
| `region` | `CORE_REGION` / `--region` | `""` | Код страны на карте сети |
| `bootstrap` | `CORE_BOOTSTRAP` / `--bootstrap` | `[]` | Адреса `core://…` для входа в сеть |
| `max_peers` | — | `8` | Целевое число соседей (исходящих — половина) |
| `gossip_interval_secs` | — | `60` | Период публикации статистики |
| `peer_check_interval_secs` | — | `10` | Как часто добирать соседей |
| `queue_ttl_secs` | — | `1814400` (21 день) | Срок хранения недоставленных сообщений |
| `log_ttl_secs` | — | `2592000` (30 дней) | Срок хранения записей журналов |
| `max_queue_messages` | — | `1000` | Лимит недоставленных сообщений в очереди |
| `max_connections` | — | `10000` | Лимит одновременных соединений |
| `idle_timeout_secs` | — | `300` | Закрывать соединение без активности |
| `cleanup_interval_secs` | — | `3600` | Период очистки по TTL |
| — | `CORE_IDENTITY_SEED` / `--identity-seed` | — | ⚠️ Только testnet: ключи из строки |
| — | `RUST_LOG` | `info` | Уровень логов (`debug` — подробно) |

## Проверка и диагностика

| Что проверить | Команда |
|---|---|
| Нода жива | `core-cli ping core://…` |
| Mailbox работает | `core-cli demo core://…` |
| Нода видит сеть | `core-cli net core://…` |
| Статус контейнера | `docker compose ps` → `(healthy)` |
| Порт открыт снаружи | с другой машины: `nc -vz 203.0.113.10 7443` |

Частые проблемы:

| Симптом | Причина |
|---|---|
| `⚠️ public_host is not set` в логах | Не задан `CORE_PUBLIC_HOST` — в адресе ноды `0.0.0.0` |
| `core-cli ping` → timeout | Порт закрыт firewall'ом / у хостера |
| `core-cli ping` → `noise: …` | В адресе неверный ключ (нода пересоздала ключи или адрес скопирован с ошибкой) |
| `peers=0` долго | Bootstrap-адрес неверен/недоступен — `RUST_LOG=debug` покажет `🔌 dial … failed` |
| Связей нет в `core-cli net` | Подождите до `gossip_interval_secs` или проверьте, что соседи достучались до адресов из дескриптора |

## Логи

Логи на английском, с эмодзи для быстрого визуального разбора. Пишутся в stderr
(в Docker — `docker compose logs`).

| Эмодзи | Событие |
|---|---|
| 🚀 | нода запущена |
| 🆔 | созданы новые ключи ноды |
| 📝 | создан конфиг по умолчанию |
| 🧪 | ключи из зерна (testnet) |
| 📡 | gossip-тик: соседи, известные/онлайн ноды, клиенты |
| 🔗 / 💔 | сосед подключился / отключился |
| 🔌 | соединение закрыто с ошибкой / не удалось подключиться (debug) |
| 🚫 | отклонена поддельная/устаревшая запись gossip (debug) |
| 🧹 | очистка по TTL |
| 🚦 | лимит соединений (debug) |
| ⚠️ / 💥 | предупреждение / ошибка хранилища |
| 🛑 | остановка |

В логах **нет** IP клиентов, идентификаторов очередей и журналов — только агрегаты и короткие ID нод.

## Безопасность и бэкап

- `identity.toml` в каталоге данных — **секретные ключи ноды** (права `0600`). Потеряете — нода получит
  новый адрес, и всем придётся обновить bootstrap. Утечёт — кто-то сможет выдавать себя за вашу ноду.
- Бэкап из Docker:
  ```sh
  docker compose cp node:/data/identity.toml ./identity.toml.backup
  ```
- `node.db` содержит только шифротексты с TTL — бэкапить не обязательно.
- Контейнер работает от непривилегированного пользователя `core` (uid 10001).
- `CORE_IDENTITY_SEED` — только для тестовых сетей.

## Разработка и CI

```sh
cargo test                                  # все тесты (unit + интеграционные с настоящими нодами)
cargo clippy --all-targets -- -D warnings
cargo fmt
```

CI — `.github/workflows/node.yml` в корне проекта: fmt + clippy, тесты на Linux и macOS, `cargo audit`,
сборка образа и публикация в `ghcr.io/<owner>/core-node` (push в `main` и теги `node-v*`; для тегов — ещё и arm64),
дымовой тест контейнера.
